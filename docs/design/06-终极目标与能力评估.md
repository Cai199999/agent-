# 06-终极目标与能力评估

> 项目：IT 运维工单智能 Agent（agent-gongdan）
> 日期：2026-11-18
> 性质：长期目标基线。后续所有功能、重构和评测均以本文六项能力为最终衡量标准。
> 当前版本：v1（可演示、可真实试用，不是生产终态）。

---

## 1. 终极目标

**把平台做成一个能承担真实 IT 运维/物业工单任务的企业级智能体系统：**

> 能理解业务任务、能规划步骤、能调用工具、能管理上下文与记忆、能被量化评估、能在高风险节点让人介入；同时具备完整后端工程体系和可观测性，而不是一个只会聊天的演示。

一句话：**不是“AI 功能集合”，而是“可度量、可运维、可审计、可扩展的业务智能体平台”。**

---

## 2. 六项终极能力标准

| 编号 | 能力 | 终极验收标准 |
|---|---|---|
| G1 | 真实业务任务 | 能独立完成报修、分诊、派单、处理、回访、知识检索、报表导出等真实任务；核心任务有量化成功率与业务收益 |
| G2 | 后端工程体系 | 数据库、权限、审计、异常、并发、幂等、异步任务、配置隔离、部署运维完整；关键路径可承载生产流量 |
| G3 | Agent 任务规划 | 能拆解目标、自主判断下一步、工具失败重试、结果校验、必要时多 Agent 协作；不是固定 prompt 的单轮问答 |
| G4 | 上下文工程与记忆 | 滑动窗口、摘要、长期记忆、用户画像、时间衰减、权限隔离；记忆与知识库分离 |
| G5 | 评估与可观测 | 每轮调用链路可追踪；成功率、耗时、token/成本、工具调用、降级率可记录、可聚合、可视化；有评测基线 |
| G6 | 人机协同 | 高风险操作 100% 人工确认；支持人工介入、转人工、回滚/补偿；不盲目自动化 |

## 4. 六项能力逐项审视

### G1 真实业务任务

**已有：**

- 表单/对话报修；
- 分诊草稿与人工确认；
- 派单、接单、解决、验证、关闭；
- 现场照片强制；
- 材料、回访；
- 知识库/RAG；
- AI 分析；
- Excel 导出与 AI 导出。

**不足：**

- 真实用户量少，暂无业务收益数据；
- 无“AI 解决率、首次解决率、平均处理时长、人工介入率”等业务 KPI；
- 报表、工作台、系统管理未接入；
- 45 列模板未落地，不能直接替代既有物业系统。

**量化目标：**

- AI 辅助解决率 ≥ 30%；
- 分诊意图准确率 ≥ 85%；
- RAG Recall@5 ≥ 80%；
- 工具任务成功率 ≥ 90%；
- 人工介入率可解释、可下降。

### G2 后端工程体系

**已有：**

- MySQL + Flyway + MyBatis-Plus；
- Sa-Token JWT + 权限码 + 票级访问控制；
- 审计日志；
- 全局异常；
- 幂等键；
- SSE/线程池/连接池；
- 开发/生产配置入口；
- 无物理外键、无业务 JOIN。

**不足：**

- 无 refresh token、CSRF、CSP；
- 无限流/熔断的分布式实现（当前登录限流为单机内存）；
- 无 CI/CD、容器化、备份恢复；
- 无生产级指标与告警；
- 部分领域服务仍直接依赖 `adapters.*`（TD01）。

**量化目标：**

- 核心接口可用性 ≥ 99.5%；
- 5xx 比例 < 1%；
- 审计覆盖率 100%（写操作、导出、高风险确认）；
- 生产部署可回滚、可备份。

### G3 Agent 任务规划

**已有：**

- 工具注册与执行；
- 最多 3 步工具循环；
- 建单/导出二次确认；
- 分诊、知识检索、相似工单、导出工具。

**不足：**

- 无显式 Planner / 任务状态机；
- 工具失败不重试（直接返回失败）；
- 无工具结果校验（如参数是否满足业务约束）；
- 无多 Agent 协作；
- 复杂任务仍依赖单轮 LLM 判断。

**终极要求：**

- 目标拆解为可执行步骤；
- 每步有判断与退出条件；
- 工具失败可重试/降级/补偿；
- 工具结果有校验与断言；
- 复杂任务可按领域拆分多 Agent，但共享统一权限与审计。

### G4 上下文工程与记忆

**已有：**

- 最近 20 条消息窗口；
- Python 侧 24 条、4000 字符截断；
- RAG 上下文预算；
- 工具结果硬截断；
- `chat_session.summary` 字段预留。

**不足：**

- 未启用会话摘要；
- 无跨会话长期记忆；
- 无用户画像；
- 无时间衰减；
- 记忆与知识库尚未分离建设。

**终极要求：**

- 分层上下文：系统提示 + 摘要 + 最近窗口 + RAG + 记忆；
- 会话摘要覆盖长对话；
- 独立记忆库，按 `tenant_id + user_id` 隔离；
- 记忆支持 TTL、来源、置信度、删除；
- 时间衰减仅用于记忆，不用于权威知识库；
- 用户画像可查看、可编辑、可关闭。

### G5 评估与可观测

**已有：**

- `traceId` 贯穿请求；
- `chat.context` / `chat.done` / `chat.tool` 日志；
- `/api/v1/health/ai`；
- API E2E 22 项；
- Playwright 4 项；
- AI 评测基线 12 条。

**不足：**

- 无指标聚合与可视化；
- 无每轮 token/成本统计；
- 无全链路追踪（OpenTelemetry）；
- 评测基线是非门禁、样本小；
- 无告警。

**终极要求：**

- 每轮调用链路可追踪：输入 → 检索 → 工具 → LLM → 输出；
- 成功率、耗时、token、成本、工具调用、降级率可聚合；
- 有 Dashboard；
- 评测集纳入迭代门禁；
- 关键异常有告警。

### G6 人机协同

**已有：**

- 建单草稿必须确认；
- AI 导出必须确认；
- 高风险工具不自动执行；
- 票级权限；
- 规则分诊兜底；
- 现场照片强制。

**不足：**

- 无通用的人工介入队列；
- 无转人工任务状态；
- 无工具执行回滚/补偿；
- 人工接管后 Agent 上下文交接未标准化。

**终极要求：**

- 高风险操作 100% 人工确认；
- 支持人工接管、暂停、回滚；
- 人工操作与 Agent 操作统一审计；
- 不盲目自动化。

## 5. 演进路线

### v1（当前）

- 可演示、可真实试用；
- 核心业务闭环；
- 轻量安全、轻量评测；
- 浏览器 E2E 基础覆盖。

### v2（生产化）

- refresh token / CSRF / CSP / 分布式限流；
- 指标聚合、成本统计、Dashboard、告警；
- 会话摘要、上下文预算观测；
- 通用人工介入与转人工；
- 前端组件继续拆分；
- 浏览器 E2E 覆盖派单/解决/材料/回访。

### v3（智能体化）

- 显式 Planner + 任务状态机；
- 工具重试、结果校验、补偿；
- 多 Agent 协作；
- 独立记忆库、用户画像、时间衰减；
- 45 列导出与 AI 聚合报告；
- 评测门禁与持续回归。

---

## 6. 非目标

- 不做脱离权限和审计的“全自主执行”；
- 不把记忆混入权威知识库；
- 不为凑 45 列伪造数据；
- 不在没有评测基线时盲目调模型；
- 不让 AI 直接绕过 Java 业务规则写库。

---

## 7. 结论

当前平台是一个**优秀的 v1 原型**：业务闭环、架构边界、降级与人在回路都做得不错。

但距离终极目标，真正的差距集中在四处：

1. **Agent 规划能力不足**（G3）；
2. **上下文与记忆不足**（G4）；
3. **可观测与评测不足**（G5）；
4. **生产安全与运维不足**（G2）。

后续任何迭代，都应先回答：

> 这项改动让六项能力中的哪一项更接近终极标准？有没有可量化证据？

答不上来，就不做。

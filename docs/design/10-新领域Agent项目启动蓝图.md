## 0. 给下一个 CC 的启动说明

这份文档只回答三件事：

1. **为什么这样做**；
2. **系统应该长成什么样**；
3. **哪些边界不能越过**。

它**不包含**创建目录、安装依赖、建库、建桶、启动服务、执行迁移等具体操作。具体操作必须由下一个 CC 在获得用户明确授权后，结合当时环境自行设计并逐步确认。

开工前必须先与用户确认：

- 新 Agent 的领域边界与不负责的范围；
- 新 Agent 是独立项目，还是当前平台的扩展 capability；
- 资源登记与隔离方案（库、前缀、bucket、端口、collection）；
- 是否需要 Web 界面；
- 是否需要与当前平台或其他 Agent 互调；
- 是否有明确的验收标准和评测方式。

未确认上述事项前，不应开始写业务代码，更不应触碰任何既有项目或共享中间件。

## 1. 可行性结论

**技术上可行，推荐作为独立领域 Agent 项目启动；不建议做一个大 Agent 内嵌多个小 Agent。**

### 1.1 已经具备的基础

当前平台已经验证了完整链路：

```text
Web → Java BFF → Python AI → LLM / 向量库
         ├→ MySQL（业务写入）
         ├→ Redis（前缀隔离）
         └→ MinIO（独立 bucket）
```

并沉淀了可直接复用的架构资产：

| 资产 | 可复用内容 |
|---|---|
| 分层 | adapters / app / domain / ports；端口抽象；配置外置 |
| Agent 契约 | Manifest、Task API、状态机、确认令牌、委托令牌、SSE 事件 |
| 权限 | Actor / 角色 / 票级权限 / dataScope / 审计 |
| 可靠性 | 幂等键、条件更新、状态机、熔断、规则兜底 |
| 可观测性 | traceId、taskId、correlationId、指标、聚合端点 |
| 测试 | 单元契约、运行时契约、API E2E、浏览器 E2E |
| 工程约束 | 无物理外键、无业务 JOIN、Java 唯一写入方、Python 无状态 |

### 1.2 可复用的是“模式”，不是“运行时”

新 Agent **不应**：

- 复用当前项目的业务库表；
- 复用当前项目的聊天会话与工具实现；
- 复用当前项目的内部令牌或密钥；
- 直接把当前项目的 Java/Python 进程当作自己的运行时；
- 把当前项目的 Agent 当作自己的内部模块。

应当复制的是：

- 分层与端口设计；
- Task/Manifest/确认/委托契约；
- 资源隔离方式；
- 可观测性与测试方法；
- 文档与阶段推进方式。

### 1.3 主要风险

| 风险 | 说明 | 应对思路 |
|---|---|---|
| 资源冲突 | 题库/前缀/bucket/端口被其他项目占用 | 先登记、先复核；冲突即停，不清理他人资源 |
| 共享中间件容量 | 新 Agent 连接池、向量检索、对象存储可能影响其他项目 | 独立连接池上限、限流、独立 collection、独立 bucket |
| 身份模型分裂 | 每个 Agent 自建用户/角色，未来无法协同 | 从第一天定义 actor/tenant/roles/scope 契约 |
| 数据一致性 | 跨 Agent 复制业务数据导致漂移 | 只传引用 ID，不共享表；以源系统为准 |
| 跨 Agent 安全 | 转发内部令牌或越权上下文 | 委托令牌 + 目标白名单 + 目标端二次鉴权 |
| 可观测性割裂 | 各 Agent 日志/指标无法关联 | 全链路 `correlationId` + 统一指标命名 |
| 过早编排 | 多 Agent 路由/规划未成熟就上 | 先做独立领域 Agent，后做薄 Orchestrator |

**结论：可行性高；真正需要提前设计的是隔离、身份和契约，而不是业务代码。**

## 2. 第一个决策：新 Agent 还是当前平台的 capability

先做判断，再动手。

### 2.1 应作为当前平台的新 capability

满足以下多数条件：

- 与工单/物业报修强耦合；
- 复用同一套用户、权限、工单数据；
- 只是增加新的工具、查询或动作；
- 不需要独立部署、独立扩缩容；
- 失败会影响主流程，且应共享同一事务边界。

### 2.2 应作为独立领域 Agent 项目

满足以下多数条件：

- 有独立领域模型与术语；
- 有独立数据与生命周期；
- 有独立权限边界或租户边界；
- 需要独立部署、独立扩缩容、独立故障隔离；
- 未来会被 Orchestrator 或其他系统调用；
- 不希望与当前平台的发布节奏绑定。

### 2.3 本条项目的默认选择

**默认选择独立项目 + 独立 Agent 服务。**

只有确认“强耦合、共享数据、无需独立部署”时，才回到当前平台增加 capability。

## 3. 目标架构

### 3.1 总体拓扑

```text
未来 Orchestrator（可选、薄层）
  │
  ├── Property Maintenance Agent（当前项目）
  ├── New Domain Agent（本项目）
  └── Other Domain Agents（后续）
```

每个 Agent 都是：

- 独立项目/独立构建产物；
- 独立进程或独立服务；
- 独立数据存储与对象存储命名空间；
- 独立 Manifest 与能力集合；
- 独立权限、审计、指标与测试基线。

### 3.2 推荐分层

```text
adapters/    HTTP、持久化、AI、存储、消息、安全、指标
app/         用例编排、任务状态机、确认、幂等、权限调用
domain/      领域模型、契约、纯业务规则
ports/       对外部依赖的抽象接口
```

强制原则：

1. 业务逻辑不直接依赖具体 SDK；
2. 所有外部依赖通过端口访问；
3. 配置外置，端点/超时/池大小/并发数不硬编码；
4. 写入方唯一：数据库写入集中在一个服务内；
5. AI/推理服务保持无状态，不直接写业务库；
6. 不为省事绕过分层。

### 3.3 前端与 BFF

- 如果新 Agent 需要人工界面，使用独立 Web；
- 前端只访问本 Agent 的 BFF，不直连数据库、对象存储或 AI 服务；
- BFF 是权限、事务、幂等、审计、状态机的唯一入口；
- 如果新 Agent 只被其他 Agent 调用，可以没有 Web，只保留 Task API 与管理端点。

### 3.4 Orchestrator 的位置

Orchestrator 是**未来的薄层**，不是当前项目的一部分：

- 负责跨领域任务路由与状态汇总；
- 不直接访问各 Agent 的数据库；
- 不共享聊天上下文；
- 不绕过各 Agent 的权限与人工确认；
- 在没有明确调用量与路由需求前，不建设。

主 Agent 接入具体子 Agent 时，可直接复制：
`docs/usage/PropertyMaintenanceAgent-主Agent接入使用说明.md`
（部署、鉴权、Task、确认、事件、附件、能力、错误码、指标、限制、验收清单）。

## 4. Agent 对外契约

新 Agent 从第一天就应具备“可被调用”的形态，而不是先做内部接口以后再造。

### 4.1 Manifest / Agent Card

必须能回答：

- 我是谁、版本是什么、协议是什么；
- 我支持哪些能力；
- 每个能力的输入、输出、权限、是否需确认；
- 我的执行模式（同步/异步）；
- 我的鉴权方式；
- 我的上下文参数与限制；
- 我的可观测性端点；
- 我是否支持下游调用。

Manifest 是稳定契约，不是调试信息。

### 4.2 Task API

建议的最小语义：

```text
POST   /agent/v1/tasks
GET    /agent/v1/tasks/{taskId}
POST   /agent/v1/tasks/{taskId}/confirm
POST   /agent/v1/tasks/{taskId}/cancel
GET    /agent/v1/tasks/{taskId}/events
GET    /agent/v1/tasks/{taskId}/events/stream
GET    /agent/v1/metrics/summary
```

Task 请求应包含：

- `taskType` / `input`；
- `clientTaskId`（幂等）；
- `executionMode`（SYNC/ASYNC）；
- `contextRefs`（只传引用）；
- `parentTaskId` / `correlationId`；
- `deadlineAt` / `budget`（可先只记录）。

### 4.3 状态机

```text
PENDING → RUNNING → WAITING_CONFIRM → SUCCEEDED / FAILED / CANCELLED
```

要求：

- 状态迁移用条件更新，避免取消后被 Worker 覆盖；
- 每次迁移写事件；
- 终态不可逆；
- 任务只能被同 Actor 或合法委托方读取/确认/取消。

### 4.4 确认与幂等

- 高风险写操作默认 `WAITING_CONFIRM`；
- 确认令牌短时效、一次性、绑定 Actor；
- 未确认不得写业务数据；
- `clientTaskId` 在 Actor 维度幂等；
- 重复提交返回同一任务，不重复执行。

### 4.5 版本与兼容

- 契约变更必须升级 Manifest 版本；
- 新增字段默认可选；
- 删除/改变语义必须走新版本；
- 契约测试必须与 Manifest 版本同步；
- 旧调用方不传新字段时，行为保持兼容。

## 5. 资源与中间件复用架构

### 5.1 核心原则

共享中间件**只允许连接使用，严禁修改**。

新 Agent 必须拥有自己的逻辑命名空间：

| 资源 | 隔离要求 |
|---|---|
| MySQL | 独立逻辑库或独立 schema；独立最小权限账号；禁止写入他人库 |
| Redis | 独立 DB index 或强制统一 key 前缀 |
| MinIO | 独立 bucket |
| 向量库 | 独立 collection / index / 数据目录 |
| 端口 | 使用登记过的本项目端口段 |
| 进程 | 独立 PID、独立日志、按精确 PID 停止 |

### 5.2 绝对不允许

- 重启、停止、删除、重建共享容器；
- 修改共享中间件配置、密码、挂载、端口；
- `FLUSHALL` / `FLUSHDB` / `SHUTDOWN`；
- `DROP DATABASE`、跨库 `DROP/TRUNCATE/ALTER` 他人表；
- 全库 `KEYS *` / `SCAN` 扫描；
- 按进程名批量杀进程；
- 清理、重置或“腾出”他人资源。

### 5.3 发现冲突时

立即停止当前任务，向用户报告：

- 被占用的是什么；
- 被谁占用；
- 证据是什么。

**宁可任务不做，也不得影响其他项目。**

### 5.4 容量与噪声

共享中间件意味着容量不是独占的。新项目设计时必须考虑：

- 连接池上限；
- 请求并发与限流；
- 向量检索批量大小；
- 对象存储大文件与临时文件；
- 长任务与后台任务隔离；
- 慢查询与重试退避。

这些问题应在架构阶段确定，而不是上线后补救。

## 6. 身份、权限与上下文

### 6.1 身份契约

所有调用必须明确：

- `tenantId`；
- `actorId`；
- `roles` / `permissions`；
- `dataScope`；
- `traceId` / `correlationId`。

新 Agent 不得假设“调用方已经鉴权”，必须做自己的权限校验。

### 6.2 委托而不是转发

跨 Agent 调用时：

- 使用为目标 Agent 签发的短时委托令牌；
- 不转发源 Agent 的内部令牌；
- 委托令牌声明 Actor、角色、scope；
- 委托令牌不能再次委托；
- 目标端仍做票级/资源级权限校验。

### 6.3 上下文传递

只传引用，不传完整聊天历史：

```text
contextRefs = {
  kind: TICKET | RESOURCE | KNOWLEDGE | EXTERNAL,
  id: "...",
  revision?: "...",
  summary?: "..."
}
```

禁止：

- 其他租户/用户数据；
- 原始内部 Token；
- 绕过 dataScope 的实体 ID 列表；
- 无限长度的历史对话。

### 6.4 审计

写操作、确认、导出、跨 Agent 调用、越权尝试都应审计。

审计至少包含：

- actor / tenant；
- taskId / correlationId；
- 能力与参数摘要；
- 结果与错误码；
- 是否人工确认。

## 7. 可观测性与评测

### 7.1 三组标识

- `traceId`：一次 HTTP/任务请求；
- `taskId`：一个 Agent 任务；
- `correlationId`：跨 Agent 的调用链。

三者必须贯穿日志、指标、审计与返回体。

### 7.2 指标

建议从第一天就具备：

- 任务状态流转与成功率；
- 任务耗时 P95；
- 队列深度与活跃线程；
- 工具/能力调用次数与失败率；
- AI token 与成本（若使用 LLM）；
- 降级/熔断状态。

指标标签必须有限：

- 可以：capability、status、tool、outcome；
- 不可以：taskId、traceId、用户 ID。

### 7.3 聚合端点

应提供一个受权限保护的聚合查询端点，回答：

- 成功率；
- P95；
- 状态/能力分布；
- token 与成本；
- 工具调用分布。

实时聚合可以作为 MVP；数据量上来后替换为指标库/数仓，接口语义不变。

### 7.4 评测

- 契约测试：Manifest、Task、确认、委托、事件；
- 功能 E2E：领域主流程；
- 回归 E2E：既有能力不被破坏；
- AI 评测：若使用 LLM，建立黄金集与基线；
- 所有测试应可重复执行，且有明确通过标准。

## 8. 可靠性与升级路径

### 8.1 从第一天预留的端口

- 任务队列端口（进程内 → Redis Stream/MQ）；
- 事件流端口（轮询 → 推送网关）；
- 指标端口（Micrometer → Prometheus/OpenTelemetry）；
- 存储端口（MinIO → 其他对象存储）；
- 模型/向量端口（具体供应商 → 可替换适配器）；
- 下游 Agent 调用端口（当前可禁用）。

### 8.2 可靠性要求

- 幂等；
- 条件更新；
- 超时与重试策略；
- 熔断与降级；
- 失败可追踪、可重试、可取消；
- 关键流程有人工确认；
- 降级时仍有可用路径。

### 8.3 升级路径必须记录

每一项 MVP 妥协都应记录：

- 当前做法；
- 限制；
- 升级触发条件；
- 替换点。

没有记录的妥协视为技术债。

## 9. 部署与运行形态

推荐两种形态，从第一天就设计好：

1. **完整 BFF**：Web + 用户 API + Agent API + 管理端点；
2. **独立 Agent 实例**：只暴露 `/agent/**`、Agent Card、健康检查，隐藏用户端 API。

要求：

- 配置外置；
- 健康检查独立；
- 端口可配置；
- 日志与 PID 独立；
- 不依赖共享进程内状态；
- 未来可容器化。

## 10. 测试策略

### 10.1 测试分层

| 层 | 目标 |
|---|---|
| 单元测试 | 状态机、确认、幂等、权限、令牌 |
| 契约测试 | Manifest、Task 请求/响应、错误码、事件 |
| 运行时 E2E | 真实服务、真实中间件、主流程 |
| 回归 E2E | 既有用户 API、浏览器流程 |
| 独立实例测试 | Agent Profile 只暴露约定端点 |
| 评测 | AI 质量与业务指标 |

### 10.2 测试数据隔离

- 使用新 Agent 自己的库/前缀/bucket；
- 不写入其他项目数据；
- 测试结束清理本项目测试数据或使用可识别前缀；
- 不执行跨库清理。

### 10.3 最小验收标准

- 现有功能无回归；
- 写操作未确认不落库；
- 越权返回拒绝；
- 任务可按 taskId 追踪；
- 指标可查询；
- 独立实例不暴露用户端 API；
- 契约版本与测试一致。

## 11. 阶段推进思路

不要一次做完。按能力逐步推进：

| 阶段 | 目标 | 退出标准 |
|---|---|---|
| Stage 0 | 契约与边界冻结 | Manifest、Task、Context、Result 文档评审通过 |
| Stage 1 | 只读能力 | 只读 Task API 可用；无业务写入 |
| Stage 2 | 写能力 + 确认 | 未确认不写；确认链路可用 |
| Stage 3 | 身份与上下文 | 越权拒绝；审计完整；不泄露上下文 |
| Stage 4 | 异步与可观测 | 任务可追踪；成功率/耗时/成本可统计 |
| Stage 5 | 契约测试与独立部署 | 契约测试通过；独立实例可用 |
| Stage 6 | 评估与演进 | 有评测基线；有升级路径记录 |

每个阶段结束都应回归既有能力，而不是等最后再测。

## 12. 反模式与红线

### 12.1 架构反模式

- 做一个大 Agent，把多个领域作为内部小 Agent 嵌套；
- 每个 Agent 自建用户体系，未来无法协同；
- 直接共享业务表或跨库 JOIN；
- 前端直连数据库/对象存储/AI 服务；
- 业务逻辑直接依赖具体 SDK；
- 用聊天历史当上下文传递；
- 把 taskId 当指标标签；
- 过早做 Orchestrator；
- 为通过测试而绕过权限或确认。

### 12.2 红线

- 不修改、删除、移动、格式化当前项目之外的任何项目；
- 不重启、停止、修改共享中间件；
- 不使用他人数据库/前缀/bucket；
- 发现资源冲突立即停止并报告；
- 不物理外键、不级联删除；
- 不伪造数据或测试结果。

## 13. 交给下一个 CC 的检查清单

### 13.1 开工前必须回答

- [ ] 新 Agent 的领域边界是什么？
- [ ] 不负责什么？
- [ ] 是独立项目还是当前平台 capability？
- [ ] 数据存哪里，如何隔离？
- [ ] 是否需要 Web？谁使用？
- [ ] 是否需要与其他 Agent 互调？
- [ ] 身份/租户/权限模型是什么？
- [ ] 人工确认点在哪里？
- [ ] 可观测性指标有哪些？
- [ ] 验收标准是什么？

### 13.2 架构评审必须回答

- [ ] 这项能力未来如何水平扩展？
- [ ] 外部依赖如何替换？
- [ ] 失败/超时/重试/降级如何处理？
- [ ] 幂等键是什么？
- [ ] 越权如何拒绝？
- [ ] 审计记录什么？
- [ ] 契约变更如何兼容？
- [ ] 测试如何证明没有回归？

### 13.3 交付时必须提供

- [ ] 架构说明与边界；
- [ ] Manifest 与能力清单；
- [ ] Task/确认/委托契约；
- [ ] 数据隔离说明；
- [ ] 可观测性说明；
- [ ] 测试结果；
- [ ] 技术妥协与升级路径；
- [ ] 给调用方的接入说明。

---

## 14. 非目标

- 不在本阶段做多 Agent 协作与自动路由；
- 不做一个大 Agent 内嵌多个领域小 Agent；
- 不共享当前平台的业务库、聊天会话与工具实现；
- 不绕过权限、审计与人工确认；
- 不为快速交付牺牲隔离边界；
- 不在没有评测与回归的情况下宣称完成。

---

## 15. 一句话总结

**复制模式，不复制运行时；独立领域、独立资源、独立部署；先契约、后能力、再编排。**

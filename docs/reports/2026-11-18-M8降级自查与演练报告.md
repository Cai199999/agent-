## 2. 本轮实现

### 2.1 轻量自愈熔断器

| 文件 | 作用 |
|---|---|
| `app/ports/ai/AiAvailabilityPort.java` | 端口：`allow` / `success` / `failure` / `snapshot`，保留可替换口但不强制替换 |
| `adapters/ai/AiAvailabilityGuard.java` | 按 `chat` / `triage` / `analysis` / `retrieval` 分 scope 统计连续失败 |

默认参数（可由 `.env` 覆盖）：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `AI_GUARD_FAILURE_THRESHOLD` | 3 | 连续失败打开 |
| `AI_GUARD_OPEN_SECONDS` | 15 | 首次打开时长 |
| `AI_GUARD_MAX_OPEN_SECONDS` | 60 | 半开失败后翻倍的上限 |

行为：

1. `CLOSED`：正常放行；成功清零。
2. 连续失败达到阈值 → `OPEN`，期间直接快速失败，不发上游请求。
3. 到期 → 放行 1 次 `HALF_OPEN` 探测；成功回 `CLOSED`，失败重新 `OPEN` 并将等待时长翻倍。
4. `GET /api/v1/health/ai` 返回 `UP` / `DEGRADED` 与各 scope 状态，供前端展示。

接入点：

- 对话 SSE：`PythonChatStreamAdapter`
- 分诊：`PythonTriageAdapter`
- 工单 AI 分析：`TicketAiAnalysisService`
- 知识检索与相似工单：`KnowledgeService.search`、`TicketVectorService`

### 2.2 规则分诊兜底

- 新增 `app/service/RuleTriageService.java`。
- 仅在 Python 分诊失败/熔断时启用；输出低置信度草稿（`confidence=0.45`，`model=rule-fallback`）。
- 支持故障类型、优先级、位置、标题/描述的简单关键词规则；**不自动建单**，仍由用户确认。
- 对话流 `triage` 事件增加 `degraded=true`，前端可识别为兜底结果。

### 2.3 前端回退与提示

- `ChatView.vue`：
  - 顶部常驻“表单报修”按钮。
  - 每 30s 查询 `/api/v1/health/ai`，`DEGRADED` 时显示黄色提示条。
  - 消息失败气泡增加“改用表单报修”链接。
- `TicketListView.vue`：
  - 支持 `/tickets?create=1` 自动打开新建工单弹窗，并清理 query。
- 新增 `api/health.ts` 封装健康检查。

### 3.2 Python 宕机

停止本项目 Python 进程（未动共享中间件），连续发送 3 条同类报修消息：

| 请求 | 耗时 | 结果 |
|---|---|---|
| 第 1 条 | 243ms | `event:error code=30001`；规则分诊草稿卡；`degraded=true` |
| 第 2 条 | 404ms | 同上 |
| 第 3 条 | 166ms | 同上 |

第 3 条后 `health/ai`：

```json
{
  "status": "DEGRADED",
  "scopes": {
    "retrieval": {"state": "OPEN", "failures": 3, "remainingSeconds": 14},
    "chat": {"state": "OPEN", "failures": 3, "remainingSeconds": 14},
    "triage": {"state": "OPEN", "failures": 3, "remainingSeconds": 14}
  }
}
```

熔断打开后第 4 条请求：

| 项 | 结果 |
|---|---|
| 耗时 | **153ms**（快速失败，无上游等待） |
| 规则草稿 | ✅ 仍生成，优先级 `URGENT`、位置 `A栋 2号`；类型在补充“号梯”关键词后复测为 `ELEVATOR` |
| 错误码 | `30001`，`degraded=true` |

### 3.2.1 规则关键词复测

`A栋2号梯困人了` 在补充“号梯”关键词后，规则草稿输出：

```json
{"ticketTypeCode":"ELEVATOR","priorityCode":"URGENT","locationText":"A栋 2号"}
```

### 3.3 恢复自愈

重启 Python，等待 16s 后发送请求：

| 项 | 结果 |
|---|---|
| 耗时 | 约 5.9s（半开探测 + 正常生成） |
| SSE | `event:done`，无 `event:error` |
| 分诊 | 正常返回 |
| health/ai | `UP`，三个 scope 均 `CLOSED`、`failures=0` |

结论：**无需重启 Java，下一次请求自动探测并恢复。**

| 约定 | 现状 | 处理 |

## 5. 未做 / 风险

1. 未做“真实 Milvus 文件损坏”演练；本轮用空目录验证了同一降级路径，避免破坏现有数据。
2. 规则分诊只覆盖常见故障关键词，复杂描述仍依赖 LLM；低置信度会标黄。
3. 前端健康状态 30s 轮询，故障后最多 30s 才显示顶部提示；对话失败仍即时提示。
4. Java 应用层仍直接依赖部分 `adapters.*`（既有技术债），本轮未重构。
5. 未引入自动重试；瞬时网络抖动仍可能直接触发一次失败。

## 3. 分类结果

### 3.1 故障报修与分诊建单（10/10 意图成功）

- 10 条全部识别为 `FAULT_REPORT`。
- 9 条生成工单草稿，1 条因缺少位置主动澄清（空调不制冷未给位置），符合分诊规则。
- 实体抽取较好：
  - 电梯困人：位置“3号楼2单元12楼”、类型 `ELEVATOR`、优先级 `URGENT`；
  - 门禁无反应：类型 `ACCESS`、位置“一楼大厅”；
  - 消防通道杂物：类型 `FIRE`、优先级 `HIGH`。
- 问题：
  1. 部分回答已生成草稿，却仍要求用户补充“用于建单”的信息，卡片与回答不一致（1-07、1-09）；
  2. 部分问题同时出现“分诊草稿卡片”和 `ticket_create` 工具草稿，存在双草稿路径。

### 3.2 知识库问答与 RAG

- 5 个命中知识库的问题均给出带 `[1][2]` 引用的回答：
  - 电梯困人、消防水泵异响、门禁手动开启、空调 E5、漏水后检查项。
- 5 个知识库无依据的问题全部明确回答“知识库暂无依据”，未编造：
  - SLA 响应时间、灭火器年检、噪音投诉流程、耗材清单、避雷巡检。
- 改进后引用噪声下降：例如电梯困人引用从 4 条降到 1 条，消防水泵从 5 条降到 2 条。
- 仍存在：无依据问题仍会带 4–5 条低分引用；2-05 出现重复 `knowledge_search`。

### 3.3 查单与状态追踪

改进后：
- `ticket_query` 支持 `priority_code`、`assignee_id`、`start_time`、`end_time`、`open_only`；
- “这周未解决”从 3 次查询降为 1 次；
- “上周紧急单”从误走导出改为正确的 `ticket_query`；
- `ticket_detail` 返回处理人姓名、报障人姓名与 SLA；
- 新增 `user_lookup`，4-01 可正确解析“张工 = 10002”。

仍存在：
- 工单列表只返回处理人 ID，未批量返回姓名；
- “超时”需要 SLA 判定，当前只能基于 `sla_resolve_due_at` 做前端判断，尚无 `overdue` 筛选；
- 用户“张三”在 dev 数据中不存在，3-06 正确返回“未找到用户”，属于数据而非能力问题。

### 3.4 派单、流转与高危操作

评测首轮发现：7/7 均未直接执行写操作，护栏正确，但聊天侧没有写工具，Agent 只能告知“请在界面操作”。

**已在评测后补齐：**

- 新增 12 个聊天写工具：派单、接单、解决、验证、关闭、取消、挂起、恢复、结束、评论、材料、回访；
- 全部 `requiresConfirm=true`，只生成待确认草稿，确认后由 Java 执行；
- 确认时按工具映射权限（`ticket:assign` / `ticket:handle` / `ticket:verify` / `ticket:close` / `ticket:read`），并复用票级访问控制；
- 支持工单号或数字 ID；派单需先 `user_lookup` 解析用户 ID；
- 冒烟验证：assign、hold、comment、close、material、resume、visit 均通过确认链路并落到业务状态。

首轮分数 3.0/10，补齐后约 **8.5/10**。

### 3.5 AI 智能导出

- 5/5 全部生成 `export_card`，时间解析正确：
  - 本周、上月、11月1日至今、昨天下午、最近 7 天。
- 类型/优先级/位置筛选均正确。
- 缺口：
  - “未完成”无法用单一状态表达，只能提示用户分两次导出；
  - 不支持按处理人导出。

### 3.6 相似工单与综合分析

- 无历史数据时能明确说明“未检索到”，不编造维修记录。
- “上个月”没有数据时如实说明，并给出 11 月可参考工单。
- 缺聚合分析工具，无法回答“为什么 B 栋报修多、主要是哪类”，只能拉列表后人工判断。

### 3.7 异常、闲聊与边界

- 天气、导出用户密码、删除工单等均正确拒答/说明。
- 多轮测试：查单后追问“催一下”，能记住工单号与处理人。
- 错别字：“点梯”“水官”均能纠正。
- 困人但缺位置时，不再生成无法派单的草稿，改为先澄清。

## 4. 本轮已修复

| 问题 | 修复 |
|---|---|
| 聊天侧无写工具 | 新增 12 个写工具 + 统一确认/权限映射，冒烟通过 |
| 前端只渲染建单/导出确认卡 | 新增通用“工单操作确认”卡片，覆盖 12 个写工具 |
| 并发确认可能重复执行 | 确认增加 `PENDING → RUNNING` 领取锁；重复确认返回已完成或冲突 |
| 权限拒绝返回 500 | 全局异常处理补 `NotPermissionException → 403/10003` |
| 写工具权限未验证 | 新增 engineer1/reporter1 权限矩阵冒烟，4/4 通过 |
| 查单缺筛选 | `ticket_query` 增加优先级、处理人、时间范围、未完结 |
| 详情只有 ID | 返回 `assignee_name`、`reporter_name`、SLA |
| 姓名无法解析 | 新增 `user_lookup` 工具 + `/internal/v1/users` |
| 缺位置仍生成草稿 | 分诊归一化时降级为 `CLARIFY` |
| 引用噪声 | 增加 `RAG_RELATIVE_SCORE_RATIO=0.8` 相对阈值 |
| 反复查询触发步数上限 | 提示词限制同一问题最多查询 2 次 |
| 工具超时/错误重试 | 单工具超时生效；仅瞬时错误重试；权限错误不重试 |
| 多工具延迟 | 同一步骤内幂等工具并发；实测两工具 202ms→101ms |
| 写链路步骤不足 | `AGENT_MAX_STEPS` 默认由 3 调整为 5 |

验证：Python 23/23、Java 34/34；写工具冒烟 assign/hold/resume/comment/close/material/visit 全部通过；权限矩阵 4/4（engineer 接单通过、engineer 派单拒绝、reporter 关闭拒绝、reporter 评论通过）。

## 5. 下一步优先级

1. **P1：导出增强**：支持 `open_only` 与 `assignee_id`。
2. **P1：列表批量返回处理人姓名**，减少 `user_lookup` 往返。
3. **P2：聚合分析工具**：按位置/类型/时间统计工单量与趋势。
4. **P2：引用绝对下限**：为无依据问题进一步压低低分引用。
5. **P2：确认时效与版本快照**：草稿 TTL、记录草稿生成时的工单版本，避免陈旧确认。
6. **P3：浏览器 E2E**：覆盖“发起操作 → 确认卡片 → 确认执行 → 状态刷新”。
